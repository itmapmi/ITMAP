# Forecast Builder — Comprehensive Build Prompt for Replit

## Project Overview

Build an AI-native forecast builder that competes with IDC, Gartner, and MarketsandMarkets. Target user: enterprise strategy teams who need defensible market forecasts for board decks, M&A diligence, and strategic planning.

The product's core differentiator is a **structured multi-LLM debate** that surfaces and resolves load-bearing assumptions before generating a forecast, combined with a **primary-data-first construction approach** that does not anchor on existing analyst reports. Every forecast is fully traceable, editable, and updatable over time.

---

## Critical Architectural Principles (Read Before Building Anything)

These principles override convenience. Do not deviate without flagging.

1. **The schema is the spine.** Every model output, every storage decision, every UI element flows from a single canonical schema. Build the schema first and validate aggressively at every phase boundary. Do not let any LLM produce free-form output that bypasses the schema.

2. **LLMs do not do arithmetic.** Every number in the final forecast is computed by a deterministic Python calculation engine, not generated by an LLM. The LLM produces structured assumptions; the engine produces numbers; the LLM writes prose around the computed numbers.

3. **Primary data over analyst reports.** The system constructs market sizes from primary sources (regulatory filings, vendor disclosures, government statistics, customs data, industry associations) rather than retrieving estimates from analyst reports. Analyst data, if used at all, is treated as comparison material, not source material.

4. **Debate must change outputs.** If the multi-LLM debate produces the same forecast a single model would have produced, the debate is theater. Every debate phase must structurally surface and resolve disagreement, with cruxes either resolved through targeted research or formally accepted as scenario variables.

5. **Audit trail is the product.** Every assumption, every model output, every edit, every source is logged with provenance and exposed through the UI. The audit trail is not a logging feature; it is the surface enterprise customers pay for.

6. **Forecasts are living objects.** Every forecast can be edited, re-debated, and refreshed over time. Edits are versioned, never destructive. The system preserves both the AI baseline and the human-edited working version as parallel artifacts.

---

## Tech Stack

- **Backend:** Python (FastAPI), PostgreSQL for structured data, S3-compatible blob storage for raw model outputs and primary source documents
- **LLM orchestration:** Anthropic API (Claude), OpenAI API (GPT), Google API (Gemini) — at minimum three labs for debate diversity. Use a smaller model from a fourth lab (Mistral or DeepSeek) for the judge role.
- **Calculation engine:** Pure Python with Pydantic for schema validation, NumPy for forecast math
- **Frontend:** React/Next.js with a focus on the audit trail UI as the primary user surface
- **Data ingestion:** Scrapy or Playwright for primary source pulls, scheduled jobs for periodic refresh
- **Auth:** SSO-ready from the start (enterprise buyers require this)

## The Canonical Schema (Build This First)

Before writing any LLM orchestration code, define and validate this schema. Use Pydantic. Every field is typed. Every assumption has an ID. Every number traces to either a source ID or an assumption ID.

### Top-level objects

**`Forecast`** — the root object
- `forecast_id`, `created_at`, `schema_version`
- `boundary` → `Boundary` object
- `methodology` → `Methodology` object
- `base_year`, `forecast_horizon_years`, `currency`, `currency_basis` (nominal/constant)
- `segments` → list of `Segment` objects
- `drivers` → list of `Driver` objects
- `assumptions` → list of `Assumption` objects
- `cruxes` → list of `Crux` objects
- `scenarios` → list of `Scenario` objects
- `sensitivities` → list of `Sensitivity` objects
- `sources` → list of `Source` objects
- `audit_log` → list of `AuditEntry` objects
- `confidence_band` (directional / decision-grade / M&A-grade)

**`Boundary`** — what's in scope
- `boundary_id`
- `included_categories`, `excluded_categories`
- `geographic_scope`, `unit_of_measurement`
- `proposed_by_system`, `confirmed_by_user`, `user_edits`

**`Segment`** — a forecast segment
- `segment_id`, `parent_segment_id` (for hierarchy)
- `name`, `description`
- `base_year_value`, `base_year_value_construction` (which assumptions and sources built this number)
- `growth_assumptions` → list of assumption_ids
- `forecast_path` → year-by-year computed values (filled by calc engine, not LLM)
- `mece_validated` (boolean — must pass before forecast finalizes)

**`Assumption`** — every input that affects a number
- `assumption_id`
- `description`, `value`, `unit`
- `proposed_by_models` (which LLMs proposed this), `current_value_source` (debate consensus, user override, primary data)
- `sensitivity_rank` (computed)
- `editable_by_user` (boolean)
- `original_ai_value`, `current_value`, `edit_history` (versioned)

**`Crux`** — a load-bearing disagreement
- `crux_id`
- `contested_assumption_id`
- `positions` → list of `{model, value, reasoning}`
- `evidence_required_to_resolve`
- `resolution_status` (resolved / unresolved / scenario_variable)
- `resolution_path` (how it was resolved if resolved)

**`Scenario`** — bull/base/bear
- `scenario_id`, `name`, `narrative`
- `crux_resolutions` (which cruxes resolved which way)
- `forecast_path` (computed)

**`Source`** — every data source
- `source_id`, `source_type` (regulator / vendor_filing / government_stat / industry_association / analyst_report)
- `url`, `accessed_date`, `verbatim_quote`
- `reliability_tier` (1-3)

**`AuditEntry`** — every meaningful event
- `entry_id`, `timestamp`, `event_type`
- `actor` (model name + version, or user_id)
- `payload` (structured detail)

### Validation rules (enforce in code, not just in prompts)

- Every `Segment.base_year_value` must reference at least one `Source` or be flagged as constructed-from-drivers with named driver assumptions
- Segments must be MECE: child segments sum to parent ± tolerance, or validation fails
- No `Assumption` without an `assumption_id` referenced from at least one `Segment` or `Driver`
- Schema version is stored with every forecast; old forecasts remain readable when schema evolves

## Phase 1 — Market Boundary Definition

### Functional requirements

User types a market in natural language (e.g., "GCC corporate banking software, 2025-2030"). System extracts structured scope primitives and proposes a boundary for user confirmation.

### Build sequence

1. **Boundary extraction prompt.** Single LLM call (Claude or GPT, doesn't matter for this phase). Input: user's natural language description. Output: structured `Boundary` object draft with proposed inclusions, exclusions, geographic scope, time horizon, currency, unit of measurement.

2. **Reference taxonomy lookup.** Maintain an internal taxonomy of ~5,000 markets with standard definitions. Use semantic search (embeddings) to find the closest match to the user's request. If a match exists with high confidence, anchor the proposed boundary to that taxonomy entry. If no match, flag as `custom_scope`.

3. **Boundary confirmation UI.** Present the proposed boundary to the user with clear inclusions/exclusions. User can accept, edit specific fields, or override entirely. Maximum two rounds of edit-and-reconfirm before forcing a commit.

4. **Persist boundary.** Save to database with `proposed_by_system` and `confirmed_by_user` fields populated. This becomes the locked input for Phase 2.

### Caveats

- Do not let users skip boundary confirmation. The boundary determines everything downstream and ambiguity here corrupts the entire forecast.
- The taxonomy is not user-facing. Users see plain-language boundaries. The taxonomy is internal infrastructure for consistency across forecasts.
- For custom scopes, flag the eventual forecast as "custom scope" so users understand it is not directly comparable to standard catalog forecasts.

## Phase 2 — Socratic Interview

### Functional requirements

Adaptive question flow that captures methodology preferences, confidence requirements, drivers, discontinuities, and output constraints. Must feel like a senior analyst working with the user, not an intake form.

### Build sequence

1. **Question cluster definitions.** Implement five clusters, each with a defined set of possible questions:
   - Cluster 1: Boundary confirmation (1-2 questions, may be merged with Phase 1)
   - Cluster 2: Purpose and confidence bar (2 questions: decision context, confidence level needed, audience)
   - Cluster 3: Methodology preference (2-3 questions: top-down/bottom-up/demand-side/hybrid, base year, anchor data)
   - Cluster 4: Drivers and discontinuities (3-4 questions: which drivers matter, known discontinuities, adjacent markets to triangulate)
   - Cluster 5: Output and constraints (1-2 questions: format, source requirements/exclusions)

2. **Adaptive question selector.** After each user answer, an LLM evaluates which downstream questions remain relevant and which can be skipped or pre-filled. Cap total questions at 12, hard ceiling 15.

3. **Two interview modes.**
   - **Express mode:** 3-4 questions, system makes most defaults explicit. For directional forecasts.
   - **Full mode:** 8-12 questions adaptive. For decision-grade forecasts.
   - User selects mode at start; system can also auto-recommend based on Phase 1 context.

4. **"I don't know" handling.** Treat this as a first-class answer. System responds by explaining the default it will use and why. Converts the interview from interrogation into education.

5. **Streaming execution.** Begin retrieving relevant primary data as soon as Cluster 1 and 2 are complete. By the time the user finishes Cluster 5, data ingestion for Phase 3 should be substantially underway.

6. **Skip-with-consequences.** If user wants to skip a question, system explains the tradeoff explicitly. ("Without driver inputs, I'll use defaults from similar markets, which typically reduces forecast confidence by ~15%.")

### Caveats

- Do not show "Step 3 of 5." Show progress in analyst language ("I have what I need on scope and methodology — two more areas to cover").
- The interview output is a structured `Brief` object that becomes the locked input for Phase 3. Once committed, the brief cannot be edited mid-debate. To change it, the user restarts the debate.
- Question text matters. Spend real time on prompt engineering for each question. Bad question wording produces bad answers and corrupts downstream debate.

## Phase 3 — Multi-LLM Debate

### Functional requirements

Five-phase debate that produces a structured forecast brief with cruxes identified and resolved (or accepted as scenario variables). This is the highest-leverage phase in the system. Build this carefully.

### Build sequence

1. **Phase 3.1 — Independent generation (parallel, no cross-talk).**
   - Spin up parallel calls to 3-4 frontier models from different labs (e.g., Claude Opus, GPT-5, Gemini Ultra)
   - Each receives the same `Brief` from Phase 2 and the primary data ingested so far
   - Each produces a structured `Forecast` draft conforming to the schema — segments, growth assumptions, drivers, cruxes_anticipated, sources cited
   - Strict output validation: malformed output triggers retry with more constrained prompt, not parsing workarounds
   - **Critical prompting discipline:** Each model is explicitly instructed not to retrieve market size estimates from analyst reports. Must construct from primary data using named drivers. If a model cites an analyst estimate, it goes into `external_estimate` field for comparison, not into `base_year_value`.

2. **Phase 3.2 — Role-cast critique.**
   - Take the four independent forecasts from 3.1
   - Run four parallel critique passes, each with a different role:
     - **Bear:** find every reason the forecast is too optimistic
     - **Bull:** find every reason it is too conservative
     - **Methodologist:** ignore conclusions, attack the math (compounding errors, MECE failures, base year defensibility)
     - **Historian:** which analogous markets did this implicitly assume, and does that analogy hold?
   - Each role produces a structured list of `Objection` objects, each tied to a specific `assumption_id` from the original forecasts
   - Roles can be run on the same or different models — the role is the constraint, not the model identity. For diversity, run different roles on different models.

3. **Phase 3.3 — Crux identification.**
   - **Use a separate judge model** — different lab from the debaters, smaller and structured (e.g., Claude Haiku if debaters are not Claude, or a small Mistral/DeepSeek model)
   - Judge reads all objections from 3.2 and groups them by which assumption they target
   - Assumptions with multiple conflicting objections become candidate `Crux` objects
   - Output: ranked list of cruxes with positions (which model proposed which value), evidence required to resolve, and rough impact estimate
   - **Critical:** the judge identifies cruxes only. It does not resolve them. Resolution is Phase 3.4.

4. **Phase 3.4 — Targeted resolution.**
   - For each crux, run a focused resolution pass:
     - Pull additional primary data specifically relevant to the crux (regulator filings, vendor disclosures, comparable market actuals)
     - Frontier models argue specifically about that crux with the new data
     - Either converge to a defensible value (within tolerance band) → mark `resolved`
     - Or remain in disagreement → mark `unresolved`, becomes scenario variable
   - This is where you spend real compute. Phase 3.1 was cheap parallel generation; here you go deep on the 3-5 things that actually matter.

5. **Phase 3.5 — Consensus checking.**
   - Second judge pass (small structured model, lab-independent)
   - For each crux, validate: was the resolution actually within tolerance, or did models claim agreement while still differing?
   - Unresolved cruxes formally enter the `Scenario` pipeline — they drive the bull/base/bear cases in Phase 4

### Output of Phase 3

A `DebateBrief` object containing: validated forecast structure, resolved cruxes with values, unresolved cruxes flagged as scenario variables, full debate audit log (every model output, every critique, every resolution).

### Caveats

- **Models genuinely agree more than they should.** For well-documented markets, frontier models converge on similar priors because their training data overlaps. Mitigations: weight Bear and Historian roles heavily for well-documented markets; inject contrarian primary sources into the brief; force models to construct from drivers rather than retrieve from priors.
- **The judge is not a debater.** Keep its scope narrow — comparison and identification only. Do not ask it to reason about market dynamics. That is what the frontier models are for.
- **Cost and latency are real.** Full five-phase debate is 30-60 LLM calls and 5-15 minutes wall-clock. Express mode skips Phases 3.2 and 3.3 — runs 3.1 with a single judge synthesis at the end. Full debate is reserved for decision-grade forecasts.
- **Crux identification is the highest-leverage prompt in the entire system.** Spend disproportionate engineering time on the Phase 3.3 prompt. Iterate on it with real strategy team feedback.

## Phase 4 — The Builder

### Functional requirements

Take the `DebateBrief` from Phase 3 and assemble it into a coherent, defensible forecast artifact. The builder is a constructor, not a creator — it does not generate new analytical content. It produces five components.

### Build sequence

1. **The deterministic calculation engine (build this in pure Python, no LLM).**
   - Takes `DebateBrief` as input
   - Validates segmentation tree is MECE — fail loudly if not
   - Applies growth assumptions per segment to base year values, computes year-by-year forecast paths
   - Models correlated drivers (segments sharing drivers move together, not independently)
   - Encodes discontinuities as step functions where applicable
   - Generates sensitivity tables: vary each assumption ±10%, ±25%, recompute, capture deltas
   - Constructs scenario paths from unresolved cruxes (base, bull, bear)
   - **Every number in the final forecast comes from this engine. Never from an LLM.**

2. **Segmentation tree assembly.** Build hierarchical segments from the brief, validate MECE, attach metadata (boundary inclusions/exclusions per segment, unit of measurement).

3. **Sensitivity ranking.** Rank assumptions by impact (the top 5-10 sensitivities are the "what to watch" section).

4. **Scenario narratives (LLM-generated, but tightly constrained).** For each scenario (base/bull/bear), the builder LLM writes a 1-2 paragraph narrative based on which cruxes resolved which way. Pass only the relevant scenario fields, not the whole forecast. Constrain the prose to reference the specific cruxes — no editorial freedom.

5. **The written report.** Standard structure:
   - Executive summary (one page)
   - Market definition and methodology
   - Market sizing and forecast (segmentation tree, numbers, growth assumptions)
   - Drivers analysis (ranked by impact)
   - Scenarios (base/bull/bear with narratives)
   - Sensitivities (what to watch)
   - Sources and assumptions register
   - Methodology appendix (debate summary, cruxes, resolutions)
   
   Generate section-by-section, not in one pass. Each section receives only the schema fields relevant to it. Every paragraph maps to specific schema fields. Every number in prose references underlying assumption IDs.

6. **Quality control passes (run before user sees the report):**
   - **Internal consistency:** segments sum to totals, growth rates compound correctly, scenario numbers actually differ from base
   - **Schema completeness:** every required field populated, every number traceable to assumption ID, every source has URL
   - **Narrative coherence:** does prose match numbers? If executive summary says "growth driven by SME adoption" but drivers analysis ranks SME adoption fourth, flag the inconsistency. Use a separate QA model.
   - On any failure, regenerate only the affected section. Do not regenerate the whole report.

### Output of Phase 4

A complete `Forecast` artifact: structured data + computed numbers + written report + methodology appendix + full audit trail.

### Caveats

- **The builder is heavily constrained.** No creative freedom. Free-form prose generation is where hallucinations creep back in. The schema and debate outputs are inputs; the report is output; the path between is deterministic with light prose generation.
- **The deterministic calculation engine is real engineering work.** Probably 4-6 weeks of focused engineering for a solid v1. Do not skimp here. This is what makes numbers correct rather than plausible-sounding.
- **The report quality bar is high.** Buyers compare to Gartner deliverables. Spend real time on prose templates. The output should look like it was written by a senior analyst at a top research firm.
- **If the debate was thin, do not paper over it.** Flag low confidence; recommend re-running debate. Do not let the builder compensate for weak debate with strong prose.

## Phase 5 — Audit Trail and Iteration

### Functional requirements

Make every assumption traceable, every assumption editable, and the forecast updateable as the world changes. This is the stage that determines retention.

### Build sequence

1. **The interactive audit trail (the primary user surface).**
   - Every number in the report is clickable
   - Click reveals: immediate composition (what segments sum to this), driving assumptions (ranked by sensitivity), debate history (which models proposed what), primary data (clickable through to actual source), peer comparison (analyst estimates if available, as context)
   - Full panel beside the report, not a popup
   - Strategy teams should be able to live in this interface for hours

2. **Three editing modes.**
   - **Assumption overrides:** user changes a specific assumption value. System recomputes downstream. Original AI value preserved alongside override. Both visible in audit trail.
   - **Boundary edits:** user changes scope. May require re-running parts of construction. System warns about scope of impact before executing.
   - **Source additions:** user uploads internal data, primary research, or other context. Goes into schema as new source with user organization as provenance. Can challenge or replace AI-derived estimates.
   - **All edits versioned, never destructive.** Original AI baseline preserved. Edited version is a layer on top. Always available to compare or revert.

3. **Methodology appendix updates on edit.** When user edits an assumption, the report's methodology appendix updates to reflect the override. Hybrid artifact — AI baseline with human overrides, fully documented.

4. **Re-debate on demand.**
   - Triggered by: new data emerging, new internal context, time-based refresh
   - Targeted, not full re-run. System identifies which cruxes are affected by new context and runs role-cast debate only on those cruxes.
   - Updates only affected portions of forecast. Rest stays untouched.
   - Cost and continuity preserved.

5. **Challenge mode (the killer feature).**
   - User clicks any number in the report
   - System runs a focused mini-debate just on that number — what assumptions feed it, what would have to be true for it to change by 20%
   - Outputs new objections, new resolutions, optionally updates the assumption if user accepts
   - This is what turns the product from generator into tool

6. **Forecast diary.**
   - Every forecast accumulates history: original generation, edits, re-debates, refreshes, comparisons to actuals when available
   - Diary is itself an artifact users can show their board to demonstrate forecasting discipline
   - Creates institutional memory inside the platform — major retention driver

7. **Calibration and feedback loop.**
   - Compare past forecasts to actual outcomes when data becomes available
   - Track which models forecasted well per market type
   - Track which cruxes were correctly identified as load-bearing
   - Track which drivers were consistently more predictive than debate assumed
   - Feed this back into model selection weights, judge training data, driver weights for future forecasts
   - Instrument from day one even if you don't act on it for 12-18 months

### Caveats

- **Stage 5 determines retention.** Stages 1-4 sell the first contract. Stage 5 makes them renew. If the audit trail is shallow, if editing is clunky, if re-debate doesn't work, the product becomes one-shot and customers churn.
- **Interface complexity is real.** Power-user audit trail UI with editable schema fields, version history, and re-debate triggers is genuinely complex. Probably 30-40% of total UI engineering should go to Stage 5.
- **Calibration takes time you don't have at launch.** Be honest with early customers — system improves with the data they help generate. Many enterprise customers accept this if framed correctly.
- **Treat AI baseline and human-edited version as parallel first-class artifacts.** Six months in they will diverge. Preserve both. The AI baseline being available is what keeps the system honest.

## The Data Layer (Build in Parallel with Phases 1-3)

The system constructs forecasts from primary data, not analyst reports. The data layer is what makes this possible. This is real infrastructure work — do not underestimate it.

### Sources to ingest

- **SEC filings and equivalent regulatory disclosures** (EU, UK, Japan, GCC) — public company segment revenue
- **Sector regulators** — central banks, insurance regulators, telecom regulators, healthcare authorities — spend data, transaction volumes, customer counts
- **Customs and trade data** — UN Comtrade, national customs authorities — physical goods market sizing
- **Government statistical agencies** — census, labor, GDP composition, household surveys, industry codes
- **Industry association data** — member surveys, transaction volumes, installed base
- **Company operational disclosures** — press releases, investor presentations, earnings call transcripts

### Architecture

- **Ingestion pipelines** (Scrapy or Playwright) per source, scheduled refresh
- **Structured extraction** — turn raw filings into structured data points with provenance (URL, accessed date, verbatim quote)
- **Storage** — primary data points in PostgreSQL with full source metadata, raw documents in S3-compatible blob storage
- **Retrieval API** — debate models query the data layer for relevant primary data points given a market boundary

### Caveats

- **Coverage will be incomplete on day one.** Pick initial markets where primary data is rich (public-vendor-dominated, regulated industries, strong industry associations). Avoid emerging frontier categories until the muscle is built.
- **Each forecast adds to coverage.** Sources ingested for one market become available for others. Coverage compounds.
- **Be transparent about gaps.** When primary construction is weak, flag it in the forecast. Honesty about uncertainty is itself a differentiator.

## Anti-Anchoring Discipline (Apply Throughout)

This is the prompting discipline that prevents models from defaulting to analyst report numbers.

### In every debate prompt

- Explicit instruction: "Do not retrieve market size estimates from analyst reports (IDC, Gartner, MarketsandMarkets, Forrester, Omdia, etc.). Construct from named drivers using primary data sources."
- "If you reference an analyst estimate, place it in the `external_estimate` field with the source. It will be used for comparison only, not as a base year value."
- "Each base year value must have construction logic: identify the demographic or economic base, the adoption rate, the price point, and multiply. State each driver value with its primary source."

### In schema validation

- A `Segment.base_year_value` without underlying driver construction (or, where appropriate, a primary data point) fails validation
- An `external_estimate` field is allowed and surfaced in the report for comparison, but does not feed the calculation engine

### In the report

- Feature the construction logic prominently, not in the appendix. First section after the executive summary should show: "We sized this market by counting X public companies in scope (source), applying adoption rate Y from regulator filings (source), multiplied by spend per customer Z from primary survey data (source)."
- Where analyst estimates exist, show the comparison transparently: "Our constructed estimate is $3.7B. IDC estimates $4.2B. The 13% gap is explained by [boundary differences / scope differences / methodological differences]."

## Things to Watch For (Failure Modes)

1. **Schema drift.** Models will try to produce outputs that don't conform. Validate aggressively at every boundary. Retry with more constrained prompts, do not parse around malformed output.

2. **Anchor leakage.** Models will sneak analyst estimates into base year values even when instructed not to. Catch this in schema validation — base year values without construction logic fail.

3. **False consensus.** Three models from three labs giving the same answer is not validation — it may just be correlation in training data. Especially watch for this on well-documented markets. Force contrarian roles to push harder.

4. **LLM arithmetic.** If you ever find yourself letting an LLM compute a number directly, stop. Route through the calculation engine.

5. **Audit trail as appendix.** If the audit trail feels secondary in the UI, you have built the wrong product. It must feel central.

6. **One-shot mentality.** If users can only generate forecasts and not edit/refresh/challenge them, you have built a generator, not a system. Stage 5 is non-negotiable for retention.

7. **Calibration ignored.** If you don't instrument the feedback loop on day one, you cannot retrofit it. Even if you don't act on calibration data for 18 months, capture it from day one.

## Final Note for the Replit Agent

This system is intentionally complex because the buyer (enterprise strategy teams at Fortune 500s and equivalent) demands it. Do not simplify by removing the debate, the audit trail, or the primary data discipline. Each of these is what separates this from the dozens of "AI generates a market report" tools currently in market. The complexity is the moat.

If any architectural decision pushes toward "easier but less defensible," flag it and choose defensibility. If a feature can be deferred to v1.1 to ship faster, defer it — but never compromise on the schema, the calculation engine, or the audit trail spine.

Build in this order: schema → calculation engine → audit log → Phase 1 → Phase 2 → Phase 3 (most time here) → Phase 4 → Phase 5 → calibration loop. Data layer work runs in parallel from week 1.
