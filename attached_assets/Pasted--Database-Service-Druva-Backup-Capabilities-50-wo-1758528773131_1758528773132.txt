| **MySQL**                                                     | Druva does not publish native MySQL “Explorer” support. Protection is typically via host/VM snapshots or application-aware agent-level backups (if agent supports file / block data) rather than deep logical MySQL object-level restores.                   |
| **MSSQL (SQL Server)**                                        | Druva’s Hybrid Workloads agent supports SQL Server backups on Windows/VMs, capturing full, differential, and transaction log backups using VSS and SQL Writer. You can restore by database from recovery points. ([help.druva.com][1])                       |
| **Oracle**                                                    | Druva allows defining backup policies for Oracle via RMAN, handles full, incremental, and archive log backups, and supports retention and deletion of archived logs. ([help.druva.com][2]) Deep snapshot/Explorer-level object restores are less documented. |
| **MongoDB**                                                   | Druva does not openly document native MongoDB integration. Likely strategy is host/VM snapshot or agent-based file/block capture, rather than integrated logical document-level restore.                                                                     |
| **IBM DB2**                                                   | There is no clear public documentation of deep DB2 support. DB2 instances would generally be backed up via OS/volume snapshots or agent-level block backup, without integrated transaction-level recovery.                                                   |
| **PostgreSQL**                                                | Druva’s documentation does not clearly mention application-aware PostgreSQL support. Backups would rely on VM or file/volume snapshot plus agent capture rather than native point-in-time PostgreSQL restores.                                               |
| **Oracle RAC**                                                | Since RAC is a clustered, shared-storage environment, Druva would treat it via cluster/volume snapshots and RMAN policies rather than coordinated node-aware “Explorer” restores.                                                                            |
| **Apache Cassandra**                                          | No explicit Cassandra support in public Druva docs. Backup likely via OS/volume snapshot or ingest via agent capturing Cassandra data files, rather than per-key or column restore.                                                                          |
| **AWS Aurora**                                                | Druva’s AWS Workloads offering supports backing up RDS / Aurora DB clusters via snapshot integration and policy automation. ([help.druva.com][3])                                                                                                            |
| **Amazon DynamoDB**                                           | Druva supports backup of DynamoDB tables via its CloudRanger / AWS Workloads integration. ([help.druva.com][3])                                                                                                                                              |
| **Amazon Redshift**                                           | Redshift clusters are protected via Druva’s AWS Workloads snapshot & restore capability. ([help.druva.com][3])                                                                                                                                               |
| **Amazon ElastiCache**                                        | There is no documented deep integration for ElastiCache (Redis / Memcached). The likely backup route is via snapshots or service-native exports rather than Druva-native object-level features.                                                              |
| **Amazon MemoryDB**                                           | No public documentation of direct support for MemoryDB. Backups would rely on AWS service-level snapshot/export, with Druva orchestrating via AWS APIs.                                                                                                      |
| **Amazon DocumentDB**                                         | Druva’s AWS Workloads support includes DocumentDB instance snapshots & restores via policy automation. ([help.druva.com][3])                                                                                                                                 |
| **Amazon Neptune**                                            | Druva does not publicly document native support for Neptune. Backup would likely rely on AWS snapshot or export capabilities, with Druva coordinating via APIs.                                                                                              |
| **Amazon Keyspaces (Cassandra)**                              | For AWS Keyspaces (Cassandra variant) Druva has no published native support; expected to use export / snapshot APIs rather than internal Cassandra-level restores.                                                                                           |
| **Amazon Timestream**                                         | Druva does not disclose Timestream support. Any backup would need to rely on export or service-level snapshot operations, not deep Druva integration.                                                                                                        |
| **Azure SQL Database**                                        | Azure SQL DB is backed by Azure’s native backup; Druva would act more as orchestrator or integrate via Azure APIs rather than supplant native backup mechanisms.                                                                                             |
| **Azure Cosmos DB**                                           | Druva does not document native object-level Cosmos DB support. Backup would likely leverage Azure API export or resource snapshot orchestration.                                                                                                             |
| **BigQuery**                                                  | BigQuery is a serverless analytics DB; Druva has no documented integration. Backups must use export to storage (e.g. GCS) and orchestration external to Druva.                                                                                               |
| **Bigtable**                                                  | No documented native Bigtable support. Backups rely on GCP’s snapshot or export APIs, with Druva possibly orchestrating scheduling.                                                                                                                          |
| **AlloyDB for PostgreSQL**                                    | Not documented. AlloyDB is a managed PostgreSQL variant; backups would use snapshots/API export rather than deep Druva-aware logic.                                                                                                                          |

The backup approach would be via VM or host snapshots, or block-level capture, without full Db2 transactional restore features.                                                                 |

Druva’s role is limited to orchestrating snapshots, export APIs, or data movement, rather than offering native DB restore capability.                                                            |
